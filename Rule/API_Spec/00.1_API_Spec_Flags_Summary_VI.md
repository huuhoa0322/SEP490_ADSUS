## Hướng dẫn đọc — mục nào thật sự là ứng viên sửa Report 3.0/3.1

Không phải flag nào cũng sửa được bằng cách chỉnh Report 3.0/3.1. Có 3 nguyên nhân gốc khác nhau bị gộp chung trong 10 file module:

| Nguyên nhân gốc | Ý nghĩa | Nơi cần sửa |
|---|---|---|
| **(A) Vấn đề nội dung PRD/UCS** | Entity list, permission matrix, hoặc nội dung 1 UC bị thiếu, tự mâu thuẫn, hoặc mâu thuẫn với UC khác. | **Report 3.0 và/hoặc 3.1 — đây mới là nhóm bạn cần.** |
| **(B) Vấn đề physical schema** | `ADSUS_Physical_Schema_PostgreSQL_v1.sql` mâu thuẫn với, hoặc không implement đúng, điều mà PRD/UCS đã nói đúng sẵn. | SQL schema / TDS — sửa Report 3.0/3.1 không giải quyết được. |
| **(C) Vấn đề L2/quy tắc đề bài** | Xung đột giữa `api_design_rules_v0.2.md` và chỉ dẫn của đề bài này, hoặc 1 quyết định thiết kế khi viết spec. | `api_design_rules_v0.2.md` hoặc quyết định thiết kế — không liên quan Report 3.0/3.1. |

Bảng dưới đánh dấu mỗi dòng bằng **(A)**, **(B)**, hoặc **(C)** để bạn biết ngay Report 3.0/3.1 có phải nơi cần xem không.

## Tổng kết — những mục thật sự cần mang lại Report 3.0/3.1

Trong 19 mục theo dõi, chỉ có **6 mục là ứng viên thật sự của Report 3.0/3.1** (nguyên nhân gốc **(A)**):

| # | Report | Vị trí | Cần kiểm tra gì |
|---|---|---|---|
| 2 | Report 3.1 | UC-19 Alternative Flows AF-01 | Thêm Business Rule/Request Fields chính thức backing hành động "tự ghi kết luận thủ công sau khi Reject AI", hoặc thêm 1 UC-ID riêng. |
| 4 | Report 3.0 | §2.2.b vs §3.2 | Giải quyết mâu thuẫn nội bộ Doctor-only vs Doctor/Nurse cho việc tạo Patient Profile. |
| 5 | Report 3.1 | UC-24 boundary note | Nói rõ Draft có được phép để trống title/content hay không, thay vì để dạng suy luận. |
| 6 | Report 3.1 | UC-09 Request Fields | Xóa "Patient code", hoặc thêm attribute đó vào 1 entity trong Report 3.0 §2.2 trước. |
| 7 | Report 3.1 | UC-23 Request Fields | Xóa "Category/Topic", hoặc thêm attribute đó vào Report 3.0 §2.2.o trước. |
| 8 | Report 3.1 | UC-26 Request Fields | Xóa "Context Case ID", hoặc thêm attribute đó vào Report 3.0 §2.2.r trước. |

12 mục còn lại là gap ở physical schema (nguyên nhân gốc **(B)**) hoặc vấn đề tài liệu L2/quyết định thiết kế (nguyên nhân gốc **(C)**) — sửa Report 3.0/3.1 sẽ không giải quyết được; cần thay đổi ở schema hoặc quyết định ở `api_design_rules_v0.2.md`/TDS. Mục #1 (Module 08, flag ưu tiên cao nhất) chính là trường hợp mà **Report 3.0 và 3.1 đã đồng thuận với nhau sẵn** — physical schema mới là bên thật sự lệch pha, không phải Report nào cả.
