Cross-Module Notes

  • User identity is shared, DTOs are not. /api/v1/users/* (Module 2, Admin account management) and /api/v1/users/me (Module 1, self-service) both read/write the same Users table, but never the same DTO shape — the Admin-facing DTO omits DateOfBirth for Patient targets and never exposes password fields; the self-service DTO exposes only the caller's own editable fields.
  • The /me alias is now used in two modules — /users/me (Module 1) and /cases/me (Module 4) — as a deliberate, consistent convention for "this resource, scoped to the caller's own JWT identity," introduced in this v1.1 pass. It is not yet formalized in api_design_rules_v0.2.md; recommend adding a short clause for it alongside §3.2's plural-noun rule.
  • /api/v1/cases/{id} is intentionally reused across UC-08 (Medical Record), UC-19 (AI Diagnosis), and UC-12 (PDF export) rather than duplicated per UC — a Case aggregates Ultrasound Images, AI Results, and the eventual Prescription, so one detail endpoint naturally serves all three read-heavy UCs, filtered by the caller's role. The list-level access, however, is now split by actor (#24 staff, #25 Patient) rather than overloaded on one path — see the v1.1 changelog.
  • /api/v1/patient-profiles/{id}/prescriptions (Module 7) nests under a Module 4 resource — Prescription history is conceptually part of a patient's medical record even though its CRUD lifecycle (Active → Completed) is owned by the Prescription & Adherence module.
  • /api/v1/schedule-slots (Module 8) is read by three different actors with three different intents: Doctor/Nurse manage capacity (UC-15), Patient browses to book (UC-13), and the same nested /appointments sub-resource lets Doctor/Nurse see who is affected before closing a slot (UC-15 AF-02).
  • /api/v1/blog-posts (Module 10) is the single source for both UC-23 (Patient reads) and UC-24 (Admin authors) — GB-05's "Published-only for Patient" rule is enforced as a query filter inside this one endpoint, not as two separate endpoints. Unlike the Module 4 case above, this is a pure visibility filter on an otherwise identical scoping mechanism (both callers query "all posts"), so it was kept as one endpoint rather than split.
  • AI Model activation (Module 6) has a downstream effect on Module 5: PATCH /api/v1/ai-model-versions/{id} changing a version to ACTIVE is what POST /api/v1/cases/{caseId}/ai-results (UC-19) actually invokes at inference time — there is no separate "current model" endpoint; the Active version is looked up server-side. Nesting the AI Diagnosis endpoints under /cases is a URL-level convenience only — it does not imply the AI Diagnosis module's Controller/BLL code must live inside the Medical Record module in the Modular Monolith (ADR-001).
  • Prescribing (Module 7, UC-18) depends on Module 5's outcome: POST /api/v1/prescriptions is only valid once the target Case's PATCH /api/v1/ai-results/{id} confirmation has moved the Case to CONFIRMED (BR-04 of UC-18).
  • POST /api/v1/chat-messages (Module 10, UC-26) carries a soft dependency on Module 4: the UCS's own Request Fields for UC-26 include an optional "Context Case ID" so the assistant can explain a Confirmed conclusion — omitted from this catalog's summary text (per the "no request/response body" constraint) but worth surfacing here since it is a real Engagement → Medical Record coupling.

Explicit Exclusions (kept out of scope, per the source documents)

  • No endpoint for Grad-CAM/heatmap explanation — descoped in PRD §4.1x / §6.3; Doctors still see segmented regions via AI Findings (existing ai-results endpoints already cover this).
  • No endpoint for national e-ID (CCCD/BHYT/VNeID), payment/insurance, or HIS/PACS integration — explicitly out of scope (PRD §6.3).
  • No SMS or business-notification-Email endpoints — Push (API-01) is the only in-app notification channel; Email is scoped solely to the password-reset flow (endpoint #6 above).
  • No endpoint invented for "processing_ms" or a per-run AI timing record — PRD §6.1 confirms the <2s target is verified via testing/APM, not stored per inference.
  • No hard-delete endpoint exists anywhere in this catalog for medical entities (Case, AI Result, Prescription, Appointment, Ultrasound Image) — consistent with GB-03; only DELETE /api/v1/users/{id} exists, and it performs a soft-delete (see <http_status_codes> in api_design_rules_v0.2.md).
  • UC-02 (Biometric login) is retained as planned/Could-priority per FT-03 — included in the catalog for completeness, not a claim that it is implemented.

Method & Boundary Notes

  • Every state-transition UC (AI Result confirm/reject, Model Version activate/rollback, Schedule Slot close, Account lock/unlock, Blog Post publish, Intake Log confirm) uses PATCH + status field rather than an invented action verb — per §3.3 of api_design_rules_v0.2.md, action-style POST .../verb is reserved only for transitions with no natural REST mapping.
  • The exceptions that do use an action-style endpoint are POST /appointments/{id}/cancel (the mandatory cancellationReason gate is not a plain field update), POST /auth/biometric-devices (a security enrollment step, not a field update), and the Auth module's login/refresh/logout/biometric-login (no underlying resource to PATCH).
  • Reschedule (UC-14 AF-01) has no dedicated endpoint — the UCS explicitly models it as POST /appointments/{id}/cancel followed by a fresh POST /appointments, matching BR-04's "cancel old + book new, both kept" rule.
  • All list endpoints follow the mandatory pagination contract (page, pageSize, wrapped in PagedResult<T>) per §7.1 of the API rules — omitted from the Endpoint column above for brevity except where a UC-specific filter is the point of interest.
  • Naming rule tension (unresolved, flagged for the API rules document, not fixed here): service-feedback (#57) and .../progress (#32) are uncountable/mass nouns that cannot be meaningfully pluralized, which sits at odds with §3.2's literal "always plural nouns" wording. This catalog keeps them singular rather than forcing an awkward plural ("service-feedbacks", "progresses"); api_design_rules_v0.2.md should gain an explicit carve-out for this case rather than leave it as a silent, undocumented deviation.
  • Data-model gap inherited from the UCS, not introduced here: the category query param on GET /blog-posts (#58) traces back to UC-23's own GetBlogArticlesRequest Request Fields table, but the Blog Post entity in PRD §2.2.o has no corresponding stored attribute (only title, content, status, publish date). This should be raised back to whoever owns the PRD/UCS, not silently resolved at the API layer.
